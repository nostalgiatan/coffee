# 内存分配系统与字节码（2026-11-04）

> 2026-11-06:字节码部分作废。线性内存、带大小释放、陷阱保留,见 [沙盒的设计](../../explanation/sandbox-design.md)。

状态：**设计提案，未实现。** 依赖 [embedded-vm-direction](2026-11-04-embedded-vm-direction.md)（D1 解释器优先、D4 三层指针、D6 能力清单、D7 验证器）和 [aggregate-storage](2026-11-04-aggregate-storage.md)（聚合值是堆上的拥有指针）。

## 目标

1. **灵活**：同一套分配接口服务原生后端、解释器、将来的 JIT，也能换分配器实现。
2. **简单**：整个分配系统小到可以逐行审计，是体积目标的一部分。
3. **边界清晰**：每一层只承担一种保证，出问题时知道该查哪一层。
4. **资源管理几乎零开销**：所有权已经决定了释放时机，VM 不需要再付一次 GC、引用计数或类型标签的钱。

## 核心判断

Coffee 的所有权规则让**每个堆块有唯一所有者，释放点在编译期确定**。所以：

- VM 不需要 GC、引用计数、写屏障、对象头里的类型信息。
- 释放时编译器**知道块的大小**（类型布局是静态的），可以做**带大小的释放** `free(ptr, size)`，块前面不需要放头。
- 资源管理的全部成本，就是程序里写出来的 `alloc` / `free` 调用和它们的实现。优化空间只剩下：少分配，和让分配/释放本身很快。

## 分层与边界

| 层 | 内容 | 保证什么 | 是否可信（TCB） |
|---|---|---|---|
| 0 线性内存 | 一块连续字节，大小由宿主设上限，访问做越界检查 | **隔离**：沙箱代码碰不到宿主内存 | 是 |
| 1 分配器 | 在线性内存上做带大小的 `alloc` / `free`，不认识类型 | 块不重叠、不越出线性内存 | 是 |
| 2 类型胶水 | 编译器生成的布局、`X__drop`、`X__clone` | 按类型正确地释放字段 | 否（由验证器的类型规则约束） |
| 3 所有权 | 借用检查、`mv` / `clone` / 最后一次使用移动 | **语言级内存安全**：无 use-after-free、无重复释放 | 否（编译期） |
| 宿主边界 | `.cfc` 能力清单里的导入函数；`object` 句柄 | 沙箱代码只能做宿主允许的事 | 是 |

要点：**沙箱安全和语言安全是两个独立的保证。** 第 3 层有 bug（比如重复释放），最多破坏沙箱自己的堆，不会越出第 0 层。这让可信部分只剩 0、1 和宿主边界，很小。

## 决定

### M1 内存模型：一块线性内存

- 沙箱里所有可寻址数据（堆、栈上要取地址的局部、静态数据）都在一块线性内存里。
- 指针是**偏移量**，不是宿主地址。`0` 保留为空。
- 区域划分：`[静态只读数据][栈区][堆区 → 向上增长]`。栈区大小固定，溢出是确定性的陷阱，不是未定义行为。
- 标量局部变量放在 VM 寄存器/帧槽里，**不可寻址**；只有被 `&` 借用的局部才分配到栈区。

### M2 指针宽度：VM 用 32 位偏移

- 指针减半，对象更小、缓存更友好，对嵌入式直接有利。
- 越界检查是一次比较 `offset + size <= mem_len`；64 位宿主上也可以预留地址空间加保护页，省掉显式检查（wasm 的做法）。
- **MIR 的指针宽度必须参数化**：布局计算以指针大小为参数，LLVM 后端用 8 字节，VM 后端用 4 字节。不能把"指针 = 8 字节"写死在布局里。

### M3 分配接口：带大小的分配与释放，块无头

```
alloc(size, align) -> ptr        // 失败即陷阱，语言里没有"返回空指针"
free(ptr, size)                  // size 由编译器按类型布局传入
```

- 编译器在每个释放点都知道大小：class 是结构体大小；`buf` / 切片的长度在胖指针里；枚举见 M4。
- 省掉每块 8 字节的头；小对象越多收益越大。
- 这也是 D4 要求 `buf` 带长度的又一个理由。

### M4 枚举：按变体各自的大小分配（实测后改）

- 当前实现已经按变体分配：`Tree.Leaf` 8 字节，`Tree.Node(l, r)` 24 字节。
- 带大小的释放要求 `Enum__drop` 读 tag，按 tag 选出该变体的大小再 `free(ptr, size)`。
- 原先写的"v1 按最大变体统一分配"被实测否定：叶子占一半，统一成 24 字节会让叶子涨到 3 倍。见"实测"一节。

### M5 分配器算法：大小类空闲链表 + 顶部指针

- ≤ 256 字节：按 8 字节粒度分大小类，每类一条**侵入式单向空闲链表**（空闲块里存下一个指针）。`alloc` 先弹链表头，空了就从堆顶 bump。
- 大块：走一条按地址排序、带合并的空闲链表，是罕见路径。
- 单线程（一个沙箱实例一个线程），不用原子操作。
- 起点只是这样。**用基准测试决定要不要更复杂**，不要预先设计。

### M6 `alloc` / `free` 是 VM 的原生指令，不用字节码实现

- 分配是最热的操作之一，快路径应是几条机器指令。
- 代价：VM 的可信部分多约 200 行。换来的是 `ALLOC` 指令不经过解释执行。
- 用 Coffee 写一份参考实现放在测试里，用来对照原生实现的行为。

### M7 `object` 是宿主句柄表的下标，不是地址

- C 句柄在沙箱里是 `u32` 下标，宿主维护一张表。没有算术，天然符合 D4 的 `object` 层。
- 好处：宿主可以撤销句柄，沙箱伪造一个下标也只会得到"无效句柄"陷阱。
- 传缓冲区给宿主函数：宿主收到 `(offset, len)`，先校验范围，再用 `base + offset` 访问。校验是导入函数边界的一部分。

### M8 原生后端也走同一套接口

**硬性要求：声明必须带 LLVM 分配属性**（`allockind("alloc,uninitialized") allocsize(0) "alloc-family"="coffee"`，释放侧 `allockind("free")` 加 `allocptr`）。只改名不带属性，优化器就认不出这是分配，不能再消掉不逃逸的分配。数据见"实测"。

- 现在 `emit_heap_alloc` 直接调用 libc 的 `malloc`，`__drop` 直接调用 `free`。
- 改成调用运行时函数 `__coffee_alloc(size)` / `__coffee_free(ptr, size)`。原生实现可以映射到 `malloc` / `free` 并忽略 `size`。
- 好处：两个后端的释放点和大小传递一致；有一个统一的位置做**分配计数、泄漏报告、调试毒化**（现在测试用 `LD_PRELOAD` 垫片，是权宜之计）。

## 对字节码设计的影响

### 不需要的东西

- 对象头、类型标签、写屏障、引用计数指令、GC 根表。
- 运行时的 `drop` 指令：`drop` 已经被编译成对 `X__drop` 的普通调用，加最后一条 `FREE`。

### 需要的内存指令（草案）

| 指令 | 含义 |
|---|---|
| `ALLOC rd, size` | 分配 `size` 字节，`rd` 得到偏移；对齐由大小类决定 |
| `FREE rs, size` | 释放 `rs` 指向的块 |
| `LD8/16/32/64 rd, [rs + imm]`（有符号和无符号变体） | 按布局里的静态偏移读取 |
| `ST8/16/32/64 [rd + imm], rs` | 写入 |
| `MEMCOPY rd, rs, len` | `clone` 的浅拷贝部分 |
| `LDX rd, slice, idx` | 带长度检查的切片读取（融合指令） |

- **类型化指令，运行时没有类型标签**：验证器在加载时检查每条指令的操作数类型（D7），解释器无需再检查。
- **移动就是寄存器拷贝**：`mv` 和最后一次使用移动只是把指针从一个寄存器复制到另一个，常常能被寄存器分配消掉，不产生指令。
- **切片占两个寄存器**（指针、长度），不装箱。
- 指令编码倾向 **32 位定长字**（8 位操作码加三个 8 位寄存器，或加 16 位立即数）：解码快，对 JIT 友好。字节码体积和解码速度的取舍见"未决"。

### 帧与栈

- 每个函数的帧大小由编译器算出，调用时一次性预留。
- 调用深度和栈区大小有上限，超出是确定性陷阱。这直接给递归 drop 的深度问题划了边界。

### 陷阱（trap）

越界、除零、栈溢出、分配失败（超过宿主设的内存上限）都是**陷阱**，终止沙箱实例，不是未定义行为。宿主设置线性内存上限，就同时得到了资源配额。

## 效率模型

| 手段 | 作用 | 阶段 |
|---|---|---|
| 带大小释放，块无头 | 每个小对象省 8 字节 | v1 |
| 大小类链表 | `alloc`/`free` 各约几条指令 | v1 |
| 移动即寄存器拷贝 | 零额外指令 | v1 |
| 逃逸分析：不逃逸的聚合放栈区 | 去掉整个 alloc/free 对 | 之后；与 D5 同一思路（证明成立就用最直接的访问） |
| 只含标量字段的类型，drop 只剩 `FREE` | 省去逐字段 drop 调用 | v1 编译器优化 |
| Arena / 区域分配 | 整体释放，不递归 drop；适合 AST | 见下，需要先解决引用问题 |

**Arena 的难点要先说清楚：** 区域里的对象互相引用，用的是非拥有引用，而 Coffee 没有生命周期参数。可行方案是**下标式 arena**：`Id<T>` 是 `u32` 下标，没有生命周期问题，类似 Zig 和 Rust 里常见的写法。这对自举编译器的 AST 很有价值，但它是一个独立的类型设计，不放进 v1。

## 实测（2026-11-04，x86_64，glibc，clang 21）

用 `valgrind` / `heaptrack` / `LD_PRELOAD` 计数垫片 / `/usr/bin/time` 测；程序和脚本不入库，结论如下。

| 问题 | 结果 | 结论 |
|---|---|---|
| 不逃逸的分配会被优化掉吗 | 20M 次 `class` 构造 + 传参 + drop，`-O1`/`-O2` 下 `malloc=0` | 直接 `malloc`/`free` 时 LLVM 已在做逃逸消除 |
| 换成不透明 `__coffee_alloc` | 同一程序 2000 万次分配，91ms，而不是 1ms | 只改名会丢掉这个优化 |
| 加 `allockind`/`allocsize`/`alloc-family` 属性 | 又回到 0 次分配，1ms | M8 必须带属性 |
| 小对象的 glibc 开销 | 209 万个节点共请求 33.5MB，RSS 66.7MB | 16 字节请求占 32 字节 chunk，无头带大小释放理论上省一半 |
| 枚举各变体大小 | `Leaf` 8 字节、`Node` 24 字节，平均 16 | 按变体分配（见 M4） |
| heaptrack | 全部分配都是 *temporary*（分配后立即释放） | 逃逸分析在 VM 后端也值得做 |
| valgrind memcheck | 小 N 下 0 错误、全部释放 | 当前 drop 路径无重复释放、无越界 |

**测量中发现的问题**（与分配器设计无关，但会让测量失真）：

- `-O0` 下，循环里每个 `+ - *` 都在循环体里建一个 `alloca`，栈随迭代增长，约 10 万次迭代后段错误。原因是入口块已有终结指令时 `create_entry_block_alloca` 退回到"在当前块建"。已修，回归测试 `tests/stack_growth_tests.rs`。
- 带 `str` 字段并用字面量初始化的 class，drop 时 `free` 静态数据，abort（valgrind：`Invalid free ... inside data symbol "str"`）。`Class__drop` 现在对所有 class 生成，暴露面比之前大。**已修，见"`str` 的所有权"。**
- 递归枚举的 payload 绑定被当成 `int`：`Tree.Node(l, r) => count(l)` 报 `expected 'Tree', found 'int'`，非递归枚举正常。会挡住用枚举写 AST。**已修：语义分析按 scrutinee 类型逐层解析绑定类型（`pattern_bindings_typed`），不再一律声明为 `int`。**
- 循环体内声明的局部变量也被判为"非最后一次使用"，传参必须写成函数再调用；这是文档写明的保守规则，但对循环里的小对象很别扭。
- 用户函数名 `round` 与 libm 冲突，报参数个数不符。

## 与已知问题的关系

| 已知问题 | 在本设计里的位置 |
|---|---|
| `raise` 的错误对象在栈上泄漏 | 改走 `alloc`，由监听器参数的 drop 释放 |
| 深递归结构 drop 栈溢出 | 栈区上限让它变成确定性陷阱；arena 之后可以绕开 |
| 枚举 payload 里的资源不释放 | `Enum__drop` 按 tag 分发，逐字段 drop（M4 的后续） |
| `str` 字面量在静态区，`free` 会出错 | owned `str` 一律在堆上，字面量复制进堆（见"`str` 的所有权"） |
| `buf` 无长度 | M3 要求带长度，或改用切片 |

## 分阶段计划

1. **M8**：原生后端经 `__coffee_alloc` / `__coffee_free` 间接调用，`free` 带 `size`，加分配计数钩子。收益立即可见（测试不再需要 `LD_PRELOAD`），不依赖 VM。
2. **布局参数化指针宽度**（M2）。
3. 定义 IR / 字节码规范和验证器，内存指令按上表。
4. 解释器 + 原生 `ALLOC`/`FREE` + 线性内存。
5. 能力清单（D6）、句柄表（M7）。
6. 逃逸分析；下标式 arena。

## 未决

已能直接判断的：

- **栈区放进线性内存**（类似 wasm 的 shadow stack）：被借用的局部必须有地址，装箱到堆要为每次借用付一次分配，而 heaptrack 显示这类分配全是临时的。标量局部仍在寄存器里，不进栈区。
- **枚举按变体分配**：已由实测决定（M4）。
- **`str` 的所有权**：已决定并实现，owned `str` 一律在堆上。

需要先有东西才能测的：

- 指令编码：32 位定长字（解码快）还是变长编码（体积小）。要等 MIR→字节码有了原型，用编译器自身的源码编出两种编码，比体积和解码速度。编码器、解码器隔离好，换起来成本低。
- 分配器大小类的粒度和大块策略：用本文"实测"的 churn 和活跃集两个程序，加真实的编译器负载测。

## `str` 的所有权（已实现）

owned `str` 的字节在堆上，每个绑定恰好释放一次。

- 字面量放进拥有所有权的位置时复制进堆：`let` / 赋值、字段赋值、结构体字面量字段、`return`、传给 Coffee 函数的实参（`compile_hir_expr_owned`）。
- 字面量传给 C 函数仍是静态数据，是借用，不复制。
- 局部 `str` 在作用域出口释放（先于 `compile_remove` 清零变量槽）；by-value `str` 参数由被调用者释放，被移走（`return`、传给另一个调用、存入新值）则不再释放；显式 `rm` 立即释放。
- 测试：`tests/str_ownership_tests.rs`，用 `LD_PRELOAD` 计数断言 malloc 与 free 次数相等。

已知缺口：

- 给 `str` 局部重新赋值，旧值不释放（泄漏，不崩溃），与其他类型的"重新赋值不释放旧值"同一个缺口。
- C 函数返回的 `char*` 如果被绑定到 `str` 局部，会在作用域出口被 `free`，而它的所有者是 C。未验证，需要 `.cfc` 的返回类型来区分。
- 每个 owned 字面量一次分配。优化器能消掉不逃逸的（见实测），逃逸的要付一次 `malloc`。
