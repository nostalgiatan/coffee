# 现状:缺什么、有什么问题、有哪些局限

写于 0.9.0 之后。这里只列事实:做了什么由 [总体架构](architecture.md) 的路线表说,这里说没做的、做了但有限制的、已知会出问题的。证据不足的写成"未验证"。

## 1. 平台和目标

| 项 | 现状 |
|---|---|
| Linux x86-64、aarch64、riscv64(含 rva22、rva23) | 编译器、链接器、JIT、沙盒都有。aarch64 和 riscv64 **只在 qemu-user 下测过**,没有在真机上跑过;riscv64 的向量扩展(RVV)在真硬件上的行为未验证 |
| Windows | 只有编译器一侧:COFF 对象、Win64 调用约定,链接靠外部 MinGW-w64。没有展开信息(异常/回溯)、没有 Windows 加载器和运行时,JIT 和沙盒不能用 |
| macOS、iOS、32 位 | 没有。iOS 因系统不允许 JIT 明确不做 |
| 发布的包 | 只有 Linux:x86-64 原生,riscv64、riscv64-rva23、aarch64 由 x86-64 交叉编译。没有 Windows 和 macOS 的包;`v0.9.0` 的包在 `.gitattributes`、`editors/` 之前的提交上构建 |
| riscv64 的种子 | 没有。riscv64 的编译器能交叉编出并在 qemu 下自举到同样的字节,但从干净机器自举 riscv64 要先有别的机器上的编译器 |
| aarch64 种子 | 有,由 x86-64 交叉编出。在 qemu 下验证了自举不动点;真机验证交给 CI 的 `seed-aarch64` 任务,**这个任务第一次运行前未验证** |
| 编译器默认目标 | 读 `/proc/self/exe` 的 ELF 头判断运行所在的机器。没挂载 `/proc` 时判断失败,回落到 x86-64,在 aarch64 上会生成 x86 代码(此时要显式写 `--target=`) |

## 2. 链接和 C 互操作

- **动态链接只有 x86-64。** aarch64、riscv64 的 `cfld` 只做静态链接;没有这两个目标的 C 库和加载器可测,所以没写。
- **动态链接不支持:** TLS 符号(`R_X86_64_GOTTPOFF`;C 里常见的 `errno` 经 `__errno_location()`,不受影响)、显式符号版本(按默认版本绑定)、懒绑定(全部 `BIND_NOW`,启动时解析所有导入)、PIE 和地址随机化(可执行文件固定装在 0x400000)、`-g` 的符号表(动态链接时不写)、生成共享库(`-shared`)。
- **静态链接 glibc 不行。** `cfld -lc` 对 glibc 的 `libc.a` 报未定义符号:它需要 IRELATIVE、TLS 和 glibc 自己的启动代码。`libm.a` 是链接脚本,读不了。要用 glibc 只能走动态链接或 `cc`。
- **没有 `cc` 时:** 静态路径只接受内置 C 库(`rt/src/min.cf` 提供的那一小部分,没有 `printf`)和以 `<库>.o`/`lib<库>.a` 放在 `.cfc` 旁的库。aarch64、riscv64 上依赖 glibc 其余部分的 C 库没有办法链接。
- **库的定位:** 静态对象必须是 `<库>.o` 或 `lib<库>.a`,放在 `.cfc` 所在目录或其 `lib/`。同时有 `.o` 和 `.so` 时自动模式选静态的。
- **`.cfc` 的限制:** 头文件转 `.cfc` 的生成器把头文件当文本读,不做预处理,不跟 `#include`,结构体变成不透明的 `object`;写不出的函数留成注释。按值传结构体给 C、C 返回结构体:没有系统的测试(测过的是整数、浮点、指针、回调和超过 8 个参数)。
- **回调:** 能把函数值传给 C。直接把具名函数当参数(`apply(inc3, 10)`)报 `unsupported: node kind 34`;内联写匿名函数当实参解析不了。要先 `let cb: fn(...) => ... = fn ...` 再传。
- **变长参数的 C 函数** 只在内置表里有 `printf` 一类的声明;自己的库里的变长函数没有专门测过。

## 3. 沙盒和 JIT

- **函数值靠 IR 改写实现**(`sbxfn.cf`):取函数地址变成编号,间接调用变成与同形状函数的比较链。代价:调用开销随这种形状的函数数线性增长;编号对不上时落到 `unreachable`(陷阱)。验证器本身仍然拒绝任何间接转移。
- **同名函数改名是文本级的**(`cirgen.cf`):用户函数与运行时的 `c fn` 重名(`malloc`、`write`…)时,在用户源码里把标识符改成 `名__cf`。它跳过字符串、注释和 `.` 之后的名字,但 f-string 里 `{}` 内的调用不会被改(未测)。
- **沙盒地址模式:** x86 仍保留 `gs` 模式,删除条件(基址模式不高于 `gs` 的两倍开销)没达到(2.09 倍),所以暂缓。
- **沙盒加载器不支持:** 超过 32 KB 的帧、栈上传参的调用(最多 8 个整数、8 个浮点参数)被拒绝。向量循环在 aarch64 的沙盒里不生成(标量循环做全部)。
- **riscv64 沙盒只有基础指令集的验证器**,rva22/rva23 的扩展指令在沙盒里没有对应的验证规则(向量循环在沙盒外使用)。
- **JIT 只有"目标文件在内存里链接"一种方式**,没有解释器(设计如此)。Windows 没有 JIT。

## 4. 优化和性能

- 向量化器已有仿射下标、常数和运行时步长、可变步长的计数器,但:只在 rva23(RVV)、x86、aarch64 的一部分形状上启用;跨步访问在 aarch64、x86 上不向量化(`vec_wide` 只开在 rva23)。
- riscv64 相对 clang 的指令数(qemu 计数):最近一次测量 hash 1.14 倍、rva23 上 sieve 1.06 倍;其余基准没有逐个列在这里,溢出和常量重算还有残留。用 `ir/tools/rvbench/run.sh` 复测,不要信这里的数字。
- 沙盒基址模式比原生慢约 1.6 倍(解析器负载,主要是寄存器压力)。
- 增量构建的小函数内联、`--incremental -j` 的并行有效,但没有跨函数的全程序优化(LTO)。
- 没有 PGO。`cfprof` 是采样/计数工具,不回灌给编译器。

## 5. 语言和编译器

- **语法文档落后:** `SYNTAX.md` 是按第一代写的,自举编译器接受它的子集,另有少数新增;以 `CLAUDE.md` 和实际行为为准。
- **算术不陷阱:** 溢出回绕,除零不检查;越界下标会陷阱。
- **没有三目表达式、元组下标不支持。**
- **没有线程和原子操作** 的语言支持(运行时只有 `fork`/`waitpid`),我没有在树里找到对应的设计。
- **资源模型:** `object` 是 C 句柄,永不释放;切片 `b[i..j]` 不能存进 `let`;`buf` 里放资源元素时,克隆是共享的。
- **第一代的功能没有移植:** 约 120 个 Rust 测试对应的功能——`--emit-ast`、`--jit`、`-c`/`--have-c` 以外的命令行项、项目模式(`coffee.toml` 的 `[dependencies]`、包、`fetch`、`std install`、`init`)、C 依赖图生成器、运行时崩溃行为。**没有包管理器。** 详见 [stage0.md](stage0.md) 和 `coffee/compat/README.md`。
- **诊断:** 报错行号是展开后的文本行号(`--emit-flat` 可看),不是原文件行号;`-g` 的 DWARF 例外。

## 6. 构建、测试和发布

- **CI 的新任务没跑过:** `cross`(安装 qemu-user、跑三个目标的门槛)和 `seed-aarch64`(`ubuntu-24.04-arm` 真机)是新写的,在 GitHub 上第一次运行之前未验证;本地只验证了它们调用的脚本。
- **测试规模:** 各阶段 `tea test` 加 compat 的 63 个文件(1023 个用例),以及 `a64cases.py` 的 191 个 `exits` 用例(在 riscv64、rva22、rva23、aarch64、两个沙盒上)。没有模糊测试,没有针对越界/释放错误的系统化压力测试。
- **覆盖的缺口:** aarch64 和 riscv64 上只有 `exits` 型用例跑过;`rejected`、`balanced` 型在这两个目标上不适用或没跑。C 互操作在非 x86 目标上只有 `driver/tests/test_static_lib.cf` 一个测试。
- **种子是二进制,体积 0.44 MB 每个;** 每次改编译器输出都要刷新,忘了刷新会让 CI 的"seed is current"失败。
- **工作流依赖:** 发布包的构建依赖 `qemu-user` 的 apt 安装;无法联网的环境构建不了跨目标包。
