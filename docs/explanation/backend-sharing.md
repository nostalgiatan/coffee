# x86-64 和 aarch64 后端:哪些能共用

两个后端都有了(aarch64 到里程碑 3),可以看到哪些部分是重复的。这里只列比较的结果和抽取的顺序;没有抽取的代码改动。

## 现状

| 部分 | x86-64 | aarch64 | 情况 |
|---|---|---|---|
| 活跃区间 `g_live_ranges`、`g_crosses`、`g_hint_reg`、`g_place_size` | `gen_x86_regs.cf` | 直接调用 x86 文件里的 | 已经共用,只是名字和位置还写着 x86 |
| 线性扫描分配 | `g_alloc_regs`(约 130 行) | `ga_alloc_regs`(约 125 行) | 骨架重复:按起点排链表、释放过期的占用、合并(coalesce)优先、再看提示、再取空闲、没有则让最不需要的去栈上。差别是寄存器池和"跨调用"的约束 |
| 栈帧布局 | `g_layout`(约 65 行) | `ga_layout`(约 62 行) | 与 diff 对照,几乎逐行相同。差别只有三处:帧头大小(a64 多 16 字节放 fp/lr)、沙盒帧上限的写法、a64 把 `voff` 赋值放在前面 |
| 边上的拷贝(块参数) | `g_edge_copy`、`g_edge_moves`、`g_emit_move`(约 125 行,含并行拷贝的环处理) | `ga_edge_copy`(约 50 行,有冲突就走临时区) | 判断"这些拷贝是否互相有冲突"的逻辑重复;解决冲突的方式不同(x86 排序并破环,a64 过临时区) |
| 寄存器编号 `hid` | `g_hid` | `ga_hid` | 重复,只是浮点寄存器的编号起点不同 |
| 调用序列 | `g_do_call`(约 100 行) | `ga_do_call`(约 70 行) | 参数怎么放进寄存器和栈由调用约定决定,是数据;聚合参数的拷贝和返回值的取回重复一半 |
| 指令选择 | `gen_x86_isel.cf` 784 行 | `gen_a64_isel.cf` 425 行 | 按 IR 操作分派,每个操作的发出方式属于各自的 ISA,不共用 |
| 汇编器 | `asm.cf` 789 行 | `asm_a64.cf` 617 行 | 编码,不共用 |
| 向量 | `gen_x86_vec.cf` 231 行 | `gen_a64_vec.cf` 174 行 | 循环向量化的判断(能不能向量化)可以共用,发出的指令不共用 |
| 沙盒验证器 | `sbxcheck.cf` 339 行 | `sbxcheck_a64.cf` 202 行 | 解码属于各自的 ISA;规则(哪些寄存器受保护、哪些形式的访存允许)见 `sandbox-design.md` |

## 分三类

1. **能直接共用**:线性扫描的骨架、栈帧布局、边拷贝的冲突判断、`hid` 的逻辑、聚合参数的拷贝。这些是"怎么在一组寄存器和一个帧上放值",和指令集无关。
2. **只是常数不同,放进目标描述表**:寄存器池(顺序、哪些调用者保存)、帧头大小、栈对齐、沙盒占用的寄存器、浮点池、暂存寄存器、参数寄存器、帧上限。`target_x86.cf` 和 `target_a64.cf` 已经各有一部分。
3. **属于 ISA**:指令选择、编码、调用序列里的实际指令、向量指令、验证器的解码。

## 不应该做的

不建一个"通用机器指令集"让两边都翻译成它。x86 是两地址、a64 是三地址,x86 有内存操作数、a64 没有,硬统一只会让两边多一层转换。IR 本身已经是通用的那一层(`legalize` 之后只剩目标都能处理的操作)。共用的是**分配器和帧**,不是**指令**。

## 抽取的顺序和门槛

每一步都要求两边的输出不变:x86 用语料(`/tmp/corp/run.sh` 一类的,新旧编译器逐字节对比);aarch64 用 `ir/tools/a64diff.py` 和 `a64cases.py`,并比较目标文件的 sha。

1. 把 `g_live_ranges`、`g_crosses`、`g_hint_reg`、`g_place_size`、`g_count_uses` 等已共用的搬到 `regalloc.cf`,名字改成与目标无关。不改逻辑。
2. `layout`:合成一个函数,参数是 `LayoutSpec`(帧头字节数、沙盒帧上限),分配器之后调用。
3. 线性扫描:骨架提取成一个函数,读目标表(池、调用者保存的位掩码、`reg_ok` 的回调或一个"这个值能不能用这个寄存器"的数据表)。x86 的 `cm`/`restr` 约束要变成表驱动,这是最复杂的一步;a64 的池全是被调用者保存,约束为空。
4. 边拷贝:冲突判断共用,解决冲突的两种方式留在各自文件。
5. 聚合参数和返回值的拷贝;`hid`。

预计少掉 300 到 400 行重复,更重要的是改进分配器时只改一处(例如以后换成能跨调用保存的更好策略,两边同时受益)。

## 风险

- x86 的分配器有 `restr` 和调用掩码,a64 没有;把它做成表驱动时容易让 x86 的输出变化。门槛(语料逐字节相同)能立刻发现,但调试代价高,所以放在最后做。
- 两个后端同时有人改(现在 aarch64 在另一个分支上)时,抽取会产生大量冲突。抽取前要确保两边的分支已合并,抽取期间另一边不改这些文件。
