# 沙盒里的指针:偏移式寻址指针(设计,未实现)

## 问题

基址模式在 x86-64 上每次访存多一条 `lea r13d, [..]`,还占用 r13 和 r15 两个寄存器。实测(`ir/bench`,`cfjit`):访存多的程序比 `gs` 模式慢 10% 到 20%,`gs` 几乎持平。`gs` 是 x86 专有的;aarch64 的 `[x28, wN, uxtw]` 和 riscv64 的 `add.uw` 把"零扩展 32 位再加基址"放进了访存指令,没有额外开销。所以只有 x86 的基址模式吃亏。

目标:去掉 `gs`,所有目标用同一个"基址 + 偏移"模型,x86 上也接近 `gs` 的开销。

## 两种现成的指针都不合适

| 做法 | 问题 |
|---|---|
| 纯 32 位指针(wasm32、Native Client):指针占 4 字节 | 数据布局和原生不同(结构体大小、字段偏移变了),同一份 `.cir` 在沙盒和原生里的 `sizeof` 不一样;`.cfc` 的 C 互操作、`object` 句柄、`buf` 的 `{ptr, len}` 都要换布局 |
| 纯 64 位指针 + 软件边界检查(wasm memory64) | 文献里 memory64 的软件检查开销大:[Döllerer 和 Engelke (VMIL 2024)](https://2024.splashcon.org/details/vmil-2024-papers/5/Performant-Bounds-Checking-for-64-Bit-WebAssembly) 报告软件检查超过 100%,他们的两级保护页方案降到 12.7%;[Firefox 的 WasmMemory.cpp](https://searchfox.org/firefox-main/source/js/src/wasm/WasmMemory.cpp) 里 memory64 必须每次显式检查,32 位的才能靠保护页省掉 |

## 提议:偏移式指针

指针在内存里仍是 8 字节(布局和原生完全相同,同一份 `.cir`),但它的**值**是线性内存里的偏移,**寻址模式**是"区域起点 + 偏移"。它不是机器地址,也不是 4 字节整数,是一个"相对区域的索引"。关键是把这个事实交给代码生成和验证器,而不是每次访存时临时重算:

1. **规范性不变量**:沙盒代码里,一个指针寄存器的高 32 位恒为 0("干净")。
2. **用生成方式保证,不靠检查值**:
   - 指针类型的载入用 32 位载入(`mov r32, [m]`,硬件自动零扩展,没有额外指令);存入仍写 8 字节,但沙盒代码能写进去任意值,所以载入时的截断是必要的。
   - 指针算术用 32 位运算(`add r32`、`lea r32`),结果自动干净;整数转指针截断。
   - `Alloc`、`Slot`、`FnAddr`、字面量等产生指针的地方,按 32 位常量或 32 位运算产生。
3. **验证器跟踪"干净"**:验证器在解码时对每个寄存器维护"高 32 位为零"的事实(任何以 32 位目的寄存器写入的指令之后为真,64 位写入之后为假),在跳转目标处取各前驱的交集。访存指令的变址寄存器必须是干净的,基址必须是区域起点寄存器。这是一个局部的前向数据流,指令边界已经由整段解码保证,控制流只有直接转移,实现约 100 到 150 行。
4. **访存形式**:`[r15 + 干净寄存器 + 位移]`,**比例固定为 1**,位移小于保护区。比例必须是 1:干净寄存器乘以 8 可以到 32 GB,会越过 4 GB 加保护页的区域。数组下标 `p[i]` 仍先算 `lea r32, [p + i*8]`(32 位 `lea`,结果干净),再用 `[r15 + r]` 访问,和现在一样一条 `lea`。节省的是**不需要地址计算的访存**:`*p`、`p->f`(位移形式)、已经算好的地址再次使用。结构体字段访问是访存里的大头。
5. **r13 不再需要**:没有暂存地址寄存器,可分配的寄存器多一个。

这和 [Native Client](https://golang.org/s/go13nacl) 的做法同源:r15 放区域起点,索引先 `mov r32, r32` 再 `[r15 + r]`;NaCl 靠指令束和固定形式保证 `mov` 紧挨着访存,所以每次访存仍多一条指令。我们的验证器跟踪"干净"事实后,多个访存可以共用一次截断,这是比 NaCl 多出来的部分。

### 各目标

| 目标 | 载入指针 | 算术 | 访存 |
|---|---|---|---|
| x86-64 | `mov r32, [m]` | 32 位 `add`/`lea` | `[r15 + r32 + disp]`,干净由验证器的数据流保证 |
| aarch64 | `ldr w, [..]` | `add w, w, w` | `[x28, wN, uxtw]`,硬件零扩展,不需要干净不变量;位移要先 `add w` |
| riscv64(将来) | `lwu` | `addw` 后 `zext.w` 或 `add.uw` | `add.uw` 加基址再访问 |

在 aarch64 和 riscv64 上"干净"的要求更弱(`uxtw`、`add.uw` 本来就取低 32 位),所以这个设计在它们上不增加成本,只在 x86 上多一份验证器的数据流。

## 为什么不用句柄表(对象表索引)

另一种读法是"指针是对象表的索引":每次访存先查表得到基址和长度,再检查偏移。它能防对象内越界和释放后使用,但每次访存多一次间接加一次比较,开销比上面所有方案都大;且 Coffee 的 `buf`/`slice` 本来就带长度,越界已经在语言层陷阱。这条路留给需要对象级隔离的场合,不作为沙盒的基础。

## 研究的结论和局限

- 在 x86 上,**零额外指令**的形式只有 `gs` 段(Segue,[论文](https://zyedidia.github.io/papers/seguecg.pdf)报告它去掉了 SPEC 上 Wasm 开销的 44.7%)和上面这种"验证器知道索引干净"的形式。后者是我们自己的设计,**没有现成的实现可抄**,开销只能量出来才知道。
- 搜索没有找到 aarch64 上 `uxtw` 形式的实测对比资料,所以"aarch64 上没有额外开销"目前是从指令形式推出的,不是实测。
- 以下是我的推断,需要量:去掉 `lea r13d` 之后,x86 基址模式的开销大概降到 `gs` 的一两个百分点以内,条件是编译器能把大部分访存做成"干净寄存器加位移"。

## 步骤和门槛

1. **先量上限**:临时关掉 `lea r13d`(让它不安全地直接用 `[r15 + r]`,仅用于基准,不合入),在 `ir/bench` 上量能省多少。上限不够好就不做。
2. 沙盒模式下 `Load`/`Store` 中指针类型的载入改成 32 位载入;指针算术用 32 位运算。`Rp` 里要有指针和整数的区别(现在是 `int`?需要看 `types` 是否保留),这是最大的前提。
3. 验证器的"干净"数据流(x86),先作为额外检查与现有规则并行,所有测试通过后再替换 `[r15 + r13]` 规则。
4. 代码生成用 `[r15 + r + disp]`;去掉 `lea r13d`,释放 r13。
5. 去掉 `gs` 模式:`Asm.sbx`、`arch_prctl`、验证器里的 `67 65` 规则、加载器里的段设置。
6. aarch64 沙盒按同一约定写(那里本来就用 `uxtw`)。

门槛:`ir/bench` 上基址模式相对原生的开销不高于 `gs` 模式的两倍(比如 `gs` 是 5%,则不超过 10%);`test_sandbox*.cf`、`compare.sh` 全过;验证器的反例集不减。
