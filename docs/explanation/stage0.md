# 为什么用固定点检查自举,以及 Rust 版的退出路线

Coffee 的编译器有两代。第一代用 Rust 写成,在仓库根目录的 `src/` 里。第二代用 Coffee 写成,在 `coffee/` 里,叫自举编译器。这篇文章讲两件事:怎么相信第二代编译对了,以及第一代什么时候可以退出。

## 固定点检查在证明什么

第一代编译第二代的源码,得到第二代的可执行文件 `gen2`。`gen2` 再编译同一份源码,得到 `gen3`。`gen3` 第三次编译。比较 `gen2` 和 `gen3` 输出的目标文件,如果逐字节相同,就说明第二代的输出不再依赖是谁编译了它。

这个检查能发现的是编译器自己的前后不一致,比如某个构造在被编译时走一条路径,生成的程序里走另一条。它不能证明编译器是对的:如果第一代和第二代对某个构造犯了同样的错,两份文本仍然相同。所以固定点检查要和其他测试一起用,不能单独当作正确性的证据。

## 第一代现在还在做什么

- 第一次构建 `coffee2`。第二代需要某个编译器来出生。
- 运行 `coffee test`。所有阶段的测试都靠它。
- 项目模式、依赖获取、`std install`、`coffee run`、`--jit`、从头文件生成 `.cfc`、`--target` 交叉编译。第二代都还没有这些。

## 退出路线

分四步,顺序重要:

1. 冻结。 第一代只修阻碍构建和测试的问题,不加新功能。它的文档移到 `docs/legacy-rust`,开头注明已过时。这一步已经做了。
2. 提交种子。 把一份固定点的目标文件放进仓库(`coffee/driver/seed/`),`coffee/driver/tools/build-from-seed.sh` 用它加系统的 `cc` 构建第二代,不需要 Rust 和 LLVM。这一步已经做了。
3. 补齐工具。 用 Coffee 写测试运行器和一个类似 cargo 的工具链程序。编译器本身只管编译,项目、依赖、获取属于工具链,就像 rustc 和 cargo 的分工。
4. 归档。 功能对等之后,第一代移出主目录。版本号重新定义,不延续第一代的 0.3.9。

现在在第 2 步和第 3 步之间。
