# JIT 后端的设计

状态:设计稿,尚未实现。格式细节见 [IR 对象格式参考](../reference/ir-object.md)。

## 目标和边界

长期目标是体积最小的嵌入式 JIT。它不是编译器里的一个模式,而是一个独立的后端模块:读入 IR,优化,生成机器码,放进内存,跳过去执行。没有前端,没有链接器,没有 libc。

边界是我们自己划的,所以没有 ABI 问题:

- 调用方和被调用方都是同一个 IR 模块里的函数,调用约定只在模块内部有效。
- 运行时是 `rt/src/min.cf`,同样以 IR 的形式进入模块,和用户函数一起生成。
- 程序要调用外部 C 库(`.cfc`)时,v1 不走 JIT,回到普通构建。动态加载需要 `dlopen`,这与"无依赖"相悖。

## 为什么是独立模块

组件体积(静态编译器 `.text` 共 731 KB):

| 部分 | 字节 |
|---|---|
| lower | 146660 |
| gen + asm + elf | 80914 |
| types | 76369 |
| rt | 76218 |
| IR 核心 | 63152 |
| opt | 61438 |
| driver | 59519 |
| sema | 56099 |
| own | 33721 |
| ld | 26693 |
| parser | 25708 |
| lexer | 15370 |

JIT 只需要 IR 核心、opt、gen、asm 和一个加载器,约 180 KB;带上前端要 530 KB。把前端留在编译器里,JIT 通过序列化的 IR 与它对接,体积差三倍。这也决定了分工:前端产出 IR 对象,JIT 消费它。

源文件不复制。`coffee/jit/` 用 `-I` 引用 `ir/src`,自己只有格式读写、加载器和入口。

## 三块东西

```
前端 (coffee2 --emit-cir)  →  .cir  →  cfjit (读取、优化、生成、加载、运行)
                                  ↑
                             tea 管理缓存和调度
```

1. **IR 对象格式(.cir)。** `Lib` 已经把函数存成列,`save`/`restore` 在内存里做了一半工作。.cir 把同样的列写到磁盘,外加名字表、表示表、字符串和全局变量。格式是我们自己的二进制结构,不借用 ELF。
2. **后端模块 `cfjit`。** 读 .cir,可选地跑 `module_opt`,调用 `Gen`,得到平铺的代码和重定位表,交给加载器。
3. **加载器。** 一次 `mmap`,按 `.text | .rodata | .data` 布局,按重定位表就地修补,把页改成可执行,跳到入口。

`tea` 控制 JIT 模式:它决定 .cir 要不要重做(源文件内容哈希),调用 `coffee2 --emit-cir` 和 `cfjit`,并把参数、退出码传回。`tea` 本身不变大,它只是多了一个子命令。

## .cir 里存什么,不存什么

存:

- `Lib` 每个函数的列 `op rep ty a b c aux nx pv uses fwd blk`。
- 基本块 `bfirst blast pfirst plast npar`、边 `efrom eto eargs eargn`、常量池 `pool`。
- 函数表:返回表示、名字号、每函数的名字(`nm`)。
- `Names`(调用目标)、`Reps`(聚合表示)、字符串字节 `sbytes`、全局变量(名字、大小)。

不存(读入时重置):值编号表 `vn`、`attrs`、`f_fx`、`f_done`、`ext_slot`。派生数据一律不入盘,否则格式要跟着优化器的内部结构变。

编码:每列按函数分块,值用 zigzag 加 LEB128。小整数占一个字节;`nx`、`pv`、`blk` 这类相邻值差很小的列按相对前一项的差编码。预计体积是原列(每值 8 字节)的 1/5 到 1/6。

存优化前还是优化后:头里有一个标志。优化后的 IR 载入更快(只剩 gen),优化前的 IR 可以在 JIT 里按热度决定优化多少。v1 两者都支持,默认存优化后的。

## 生成和加载

`Gen` 现在把代码写进 `Asm.c`,重定位记在 `rl_at/rl_sym/rl_ty/rl_add`,符号在 `Obj`,最后 `write_elf` 打包。JIT 需要另一个出口 `image()`:

- 不写 ELF 头、符号表、`.rela.text`,直接给出平铺的 text、rodata、data 和重定位表。
- 重定位只有 `PC32` 和 `PLT32` 两种,目标是模块内的函数、`.rodata` 或 `.data`。三段放在同一块映射里,距离远小于 2 GB,所以修补就是 `target - (site + 4) + addend`,不需要跳板。
- 外部符号只剩运行时里没有、又被调用的名字。v1 里集合为空;模块的符号都能在映射内解析,解析不了就是加载错误。

加载器步骤:

1. `mmap` 读写页,大小为三段之和,段首按 16 字节对齐。
2. 拷入三段,逐条修补重定位。
3. `mprotect` 把 text 段改成读加执行,rodata 只读,data 保持读写。
4. 以 `main` 的地址为入口。没有 `main` 的模块(库)返回符号查询接口。

`min.cf` 的运行时用 `syscall` 直接实现分配、输出和退出,所以不需要任何宿主函数。

## 增量和热加载

.cir 与源文件一一对应(和 `--incremental` 的 `.o` 同粒度),键是内容哈希和所依赖接口的哈希,规则与 `driver/src/incr.cf` 一致。热加载时 `tea` 只重做变化的 .cir,`cfjit` 把变化的函数重新生成到新映射,旧函数留着直到没有调用。v1 不做,但格式和加载器接口(函数按名字号寻址)为它留了位置。

## 阶段

1. **格式(已完成)。** `coffee/ir/src/cir.cf`:`write_cir(lw) => Txt` 和 `read_cir(bytes) => Module`,单元测试做往返:前端产出 → 写 → 读 → 生成,与直接生成的机器码逐字节相同。
2. **出口。** `Gen.image()` 和重定位表导出,测试与 `write_elf` 的内容一致。
3. **加载器与入口。** `coffee/jit/`:`cfjit file.cir args`,先用 `mmap` 加 `mprotect` 直接跑 `compat` 里的程序,用输出和退出码对照普通构建。
4. **tea。** `tea jit file.cf`:调度 `coffee2 --emit-cir`、缓存、`cfjit`。
5. **体积和速度。** 记录 `cfjit` 的 .text 大小、冷启动时间(读取加生成),与 `coffee2 + ld + 执行` 对比。

每个阶段独立提交,每步都过 11 个测试集和不动点检查。

## 已知风险

- `Gen` 里有对 `Obj` 的直接引用(`o.sym`、`define`)。`image()` 要么复用这些表再导出,要么抽出一个更小的接口;倾向前者,改动最小。
- 优化器和生成器带有 `verify` 开关、`ir_dump` 等调试全局。`cfjit` 要保证它们默认关闭,否则体积和速度都白费。
- 读 .cir 必须拒绝坏输入(长度、索引越界),因为 JIT 是在执行它读到的东西。格式里放了每节长度和一个校验和,读入时先验证再用。
