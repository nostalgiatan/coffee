# 循环与调用优化的设计

第 1、2 步已经实现(见文末"已做"),其余还是设计。依据是对 fib、筛法、浮点迭代、矩阵乘、哈希五个基准的测量(Coffee `-O2` 对 gcc、clang `-O2`),和对生成的机器码的检查。

## 现状:机器码里有什么

生成的程序没有运行时外壳。fib 的可执行文件整个是 1064 字节,没有符号、没有节头、没有类型标记,类型、所有权事件和名字只在编译期存在,`-g` 时才写 DWARF。一个类的块没有头,一个 `str` 只有前面 8 字节的长度字。

留下来的不是外壳,是几处不够紧凑的地方:

- **越界检查**。每次 `s[i]` 都有一次 `cmp` 加 `jae`。这是语言规定的行为(越界要中止),C 没有,所以矩阵乘的内层循环里,每次迭代有两次检查。
- **没有强度削减**。`b[k * n + j]` 每次迭代做一次 `imul r, k, 500`,而不是让下标每次加 500。
- **循环没有旋转**。条件在循环顶部,每次迭代多一个跳转。
- **寄存器之间多余的复制**。`mov r10, rax; mov rcx, r10; mov rax, rcx` 这样的链,循环尾部的 `movaps xmm2, xmm3`。
- **序言/尾声**。保存了用不到的 `rdi`,返回路径上多一个 `jmp`,始终保留帧指针(`cfprof` 靠它回溯)。
- **递归**。fib 的两个调用都是真调用,没有展开。

## 做什么,按收益与风险排序

### 1. 机器码清理(小,先做)

在 `gen.cf` 里:复制合并(目的寄存器紧接着被覆盖的 `mov` 去掉),`lea` 做加常数的三地址形式,循环旋转(把条件放到底部,入口跳一次),返回路径跳转线程化,不保存没用到的参数寄存器。帧指针保持,`--no-frame-pointer` 以后再说。

验收:fib 的指令数、矩阵乘内层循环的指令数,各少 10% 以上。

### 2. 越界检查消除

区间分析放在 `opt.cf`,在 SSA 上做:

- 归纳变量:`for i in a..b` 里 `i` 的区间是 `[a, b-1]`,`b` 的区间来自它的定义(常数、`len(x)`、参数不知道就是未知)。
- 长度:`new_buf(T, n)` 的结果带着 `len = n` 这个 SSA 值;`buf` 局部变量不能被换掉长度,所以同一个值一直有效。
- 下标是归纳变量的仿射式 `c1*i + c2*j + d` 时,用区间运算判断是否在 `[0, len)` 内。能证明就删检查,不能证明就留着,不为此改变中止发生的位置。

矩阵乘里 `n = 500`、三个缓冲区长度是 `n*n`,三个归纳变量都小于 500,所以 `k*500 + j ≤ 249999` 可证,检查全部消除。

风险:区间分析写错会放过真的越界。测试要带反例:缓冲区长度比下标范围少 1 的程序必须仍然中止。

### 3. 强度削减和归纳变量

在循环里,`i * c` 形式的乘法(`i` 是归纳变量,`c` 是循环不变量)换成每次迭代加 `c` 的新归纳变量。已有的 `hoist_invariants` 做不变量外提,这一步接在它后面。

### 4. 循环展开

只处理计数循环:归纳变量步长是常数,上界是循环不变量,循环体不超过 24 条指令,没有调用。展开 4 倍,加余数循环。

浮点累加不能重排(语言没有 fast-math),所以展开只省循环开销,不改变依赖链,预期收益 10% 到 20%。整数归约可以拆成多个累加器,收益更大。

### 5. 递归

- **自递归内联一层**:函数体不超过 16 条指令、有两处自调用时,展开一层。叶子调用少一半的序言和尾声。
- **带累加器的尾调用消除**:`ret (add X (call f(args)))` 的形式,`X` 在调用之前算好,且加法是可结合的。改成循环,`acc = acc + X`。fib 的第二个调用因此变成循环,调用次数减半。gcc 的 fib 快 4 倍主要来自这两步。

目标:fib 从 0.36 秒降到 0.15 秒以内。

### 6. 向量化(最后)

x86-64 基线只有 SSE2:`double` 和 `int64` 一次两个,收益最多 2 倍,`float(4)` 和字节才有可观收益。前提是第 2 步已经把检查消除了,否则循环里有分支,不能向量化。

条件:内层计数循环,没有调用,访问是单位步长,不同的 `buf` 在语言里不会重叠(切片除外,切片参与时不做)。浮点归约不向量化。

## 怎么验证

- 每一步都跑 12 套测试和 `compat` 的 1023 个例子,以及自举不动点。
- 五个基准的输出(退出码)必须不变,时间用 `valgrind --tool=callgrind` 的指令数比较,不用墙上时钟。
- `--lint-perf` 里加对应的发现:有可证明的越界检查还留着、循环里有可以削减的乘法,让遗漏有地方看到。
- 区间分析加一组"必须仍然中止"的测试。

## 已做:第 1、2 步

测得的指令数(callgrind),改动前对改动后:fib 67.9 亿到 58.0 亿(少 15%),矩阵乘 18.9 亿到 13.9 亿(少 26%),哈希 20.0 亿到 16.0 亿(少 20%),筛法 13.0 亿到 10.6 亿(少 18%)。编译器编译自己的指令数多约 4%,来自新的分析。

- **机器码清理**(`gen.cf`):只有返回聚合的函数才为返回指针留 `[rbp-8]` 一格,别的函数不再 `push rdi`;移位量是常数时用立即数移位,不再装 `cl`。复制合并和循环旋转已经有(`block_order` 旋转循环,寄存器分配会合并大部分复制),所以没有再加一遍。
- **范围分析**(`opt.cf` 的 `range_checks`):在 SSA 上给整数值算区间。块参数用加宽后再收窄求不动点;进入块的分支条件(循环条件、已经做过的检查)按支配关系收窄区间,一个值不会变,所以循环头的外部入口那一条边的条件对整个循环都成立。检查 `ult x, len` 在 `x` 的区间落在 `[0, len 的下界)` 内,或有支配它的 `x < len` 且 `x` 不为负时,分支改为恒真。只给检查依赖到的值算区间,而且只在有回边、长度是常数或有对同一长度的循环条件的函数里运行。
- **循环里重复的 load**(`hoist_invariants`):循环不写内存时,一个 load 若和循环头里、或进入循环的那个块末尾(其后没有写)的 load 同一地址,就用那一个。`for i in 0..len(s)` 里的 `s[i]` 因此没有检查。
- 测试:`driver/tests/test_bounds.cf`(能证明的检查没有了,不能证明的仍然中止),另外用随机程序对照了新旧编译器的退出码。

## 已做:带累加器的尾递归消除(第 5 步的一半)

`tail_recursion`(`modopt.cf`)把"返回自己的调用"和"返回调用前算好的某值加上自己的调用"改成循环:原来的入口块的内容搬进新的循环头,循环头的参数是原参数加一个累加器 `acc`;递归位置变成带新参数和 `acc + 前一个值` 的跳回,其余每个 `ret v` 变成 `ret acc + v`。加法回绕,顺序不影响结果。只处理返回 `int` 的函数,调用前后之间只能有无副作用的指令。

fib 因此每次迭代只剩一个调用:指令数 58.0 亿到 48.0 亿(少 17%),运行时间 0.36 秒到 0.25 秒;累计起来 fib 的指令数比这一轮开始前少 29%。`ack` 这类不是这两种形状的递归不变。

测试在 `driver/tests/test_recursion.cf`,另外用随机的递归函数对照了新旧编译器。

## 试过没留下:第 3、4 步

两步都先量了收益,收益不够,没有进编译器。

- **强度削减**。做了一遍(给循环头加一个每次加常数的新参数,代替 `i * c` 的乘法),矩阵乘内层循环里的 `imul` 确实变成了 `add`。但指令数不变(13.89 亿对 13.90 亿),运行时间不变(0.07 秒):`imul` 延迟 3 个周期,被浮点乘加的依赖链盖住了,乘法不在关键路径上。没有可测的收益,而这一遍给每个有乘法的循环增加了改写 SSA 的风险,所以去掉了。乘法在关键路径上的整数循环可能有收益,现在的五个基准里没有。
- **循环展开**。没写 pass,先在源码里把矩阵乘内层循环手工展开 4 倍加余数循环。指令数反而多 16%(16.1 亿对 13.9 亿,余数循环和下标的检查没消掉),时间同样 0.07 秒。浮点累加不能重排,依赖链一样长,展开省下的循环开销被流水线隐藏了。整数多累加器归约理论上有收益,但五个基准里没有这种形状,先不做。

两步的结论是:余下和 gcc 的差距在自递归内联和向量化上,不在循环开销上。

## 已做:自递归内联一层(第 5 步的另一半)

`self_inline`(`modopt.cf`)在函数其余优化做完之后,先把这个优化后的函数存进 `lib`,再把它里面的自调用(最多 2 处,函数体不超过 40 条指令,展开后不超过 120 条)各换成这份副本,然后再优化一遍。因此 `module_opt` 里的内联策略不变(调用自己的函数仍不当被调用者内联),只是在存盘前多展开一层。

fib:指令数 48.0 亿到 35.2 亿(少 27%),运行时间 0.25 秒到 0.18 秒(gcc 0.09,clang 0.16);从这一轮开始前算,指令数少 48%。`tri`、`ack` 的结果不变,150 个随机递归函数对照旧编译器的退出码全部相同。

## 向量化之前先补的:标量循环的质量

要做向量化,先量了它能买到什么。`a[i] = a[i] * 0.5 + b[i] + 1.0`(10 万个 `double`,重复 2 万遍):

| 实现 | 时间 |
|---|---|
| gcc `-O2 -fno-tree-vectorize`(标量) | 0.48 秒 |
| gcc 15 `-O2`(自动向量化) | 0.31 秒 |
| Coffee,缓冲区是局部变量 | 1.18 秒 |
| Coffee,缓冲区经 `&buf<float>` 参数传入 | 1.36 秒 |

向量化只比标量快 1.5 倍;我们的标量循环比 gcc 的标量慢 2.4 到 2.8 倍。差距在标量代码里,不在向量化上。这句里「缓冲区元素只有 8 字节」是我当时说错了:`buf<f32>`、`buf<u8>` 等从来就支持(用别名 `f32`、`u8` 写),所以向量化的上限是 4 倍(`f32`)到 16 倍(`u8`),见下一节。

补了三处(`opt.cf`、`lower.cf`):

- **加常数的链合并**:`(x + c1) + c2` 改成 `x + (c1 + c2)`(`reassoc_adds`),下标 `i + n + 37` 少一条 `lea`。
- **浮点存储不挡整数读**:循环里只有浮点存储时,指针和长度这类整数读不会被它改掉,所以可以外提(`hoist_invariants` 的 `memf`)。
- **引用参数的读可以提前**:`&T` 参数指向的内容在函数的任何位置都能读,所以循环里读它的头部(`buf` 的指针和长度)可以搬到循环前,不用等循环确定会进入。引用参数在降低时标记(类型字段 0),`deref_ok` 认这个标记。同一地址的多次读合并成一次。

`&buf<float>` 那个例子 1.36 秒到 0.93 秒;矩阵乘、哈希、fib 的指令数不变。代价:编译器自己的体积从 903 KB 到 942 KB(自递归内联展开了编译器里的递归函数)。

还剩的差距(量到但没做):

- fib 和 gcc 的差距:看了两边的机器码。gcc 把递归展开了五层左右(栈帧 184 字节,一次调用代替约 8 个叶子);我们展开一层。试过把 `self_inline` 做到三层,指令数反而多 9%(38.3 亿对 35.2 亿),时间不变,因为展开出来的每层都每次调用还要保存四个被调用者保存的寄存器和帧指针。原先写的「缺少沿路径的条件传播」是错的:`n >= 2` 推不出 `n - 1 < 2` 的真假,展开出来的判断本来就消不掉。把 `self_inline` 放到 `tail_recursion` 之前再展开两层也试过,指令数 44.4 亿,时间 0.20 秒,比现在更差。没有改。

## 已做:浮点常量池、循环倒置

- **浮点常量池**(`gen.cf`、`asm.cf`):浮点常量不再用 `movabs rax, 常数; movq xmm, rax` 两条指令,而是放在函数自己代码的末尾(8 字节对齐,同一个节,gc 时一起走),用 `movsd xmm, [rip+偏移]` 读。偏移是对函数自己的符号的重定位,分支缩短之后按标号的新位置改写。沙箱代码仍用旧办法。上面那个循环 1.18 秒到 0.89 秒,nbody 的输出不变。
- **循环倒置**(`invert_loops`,`opt.cf`):`while c` 形的循环(条件在头部)的循环体,只在条件成立时才跑,所以其中读不变量的 load 不能提到循环前。把头部的条件复制一份放在进入循环的块末尾和每个跳回的块末尾,循环头就只剩循环体,体里的 load 满足已有的外提条件。只对「体里有可外提又还没被外提的 load」的循环做;头部只能有几条纯指令;出口只有一个,且没有别的块进入;其他出口只能去检查失败的块。循环后用到的头部参数,在出口块上补一个参数。在 `module_opt` 的最后做(边界检查消除之后),所以已证明的检查不受影响。矩阵乘、哈希、筛法的指令数不变,编译器编译自己的时间不变(0.56 秒)。测试 `test_hoist.cf`、`test_invert.cf`。

## 已做:向量化(第 6 步)

`vectorize`(`opt.cf`)把「一个计数循环,循环体里一个存储」的循环,在它前面加一个一次做一个向量的循环(`Op.VLoop`),原来的标量循环留在后面做余下的元素,也兜底。

- **认的形状**:`for i in 0..n`,头部只有 `i < n`;循环体是若干 `i < 长度` 的检查(失败去陷阱块)和一个存储 `buf[i] = e`;`e` 由 `buf[i]` 的读、循环不变量、和 `+ - * /`(浮点)、`+ - & | ^`(整数;`*` 只有 16 位的)组成。小整数元素按「扩展、计算、截断」的写法认,等价于在元素宽度上回绕的运算。元素是 `f32`(4 个)、`f64`(2 个)、`i8`/`u8`(16 个)、`i16`(8 个)、`i32`(4 个)、`i64`(2 个)。
- **检查**:循环前先算 `n <= 每个检查用到的长度`;成立才走向量循环,否则直接走标量循环,所以越界仍在原来的位置中止。
- **别名**:所有访问下标都正好是 `i`,所以两个形参指向同一个缓冲区也没有问题;一个循环只允许一个存储,这样不会出现「后面的表达式重新读到前面存进去的值」。
- **机器码**(`gen.cf` 的 `gen_vloop`):按调用处理(用 rax rcx rdx rsi rdi r8..r11 和全部 xmm),参数先压栈再弹进固定的寄存器;不变量在循环外拼成整个向量放进 xmm8 起的寄存器;循环体按后序程序逐项翻成 `movups`、`addps`/`paddb` 等。沙箱代码里这条指令什么也不做(返回起点),由标量循环做完。
- **读指针和长度**:`u8`、`i32` 这类小整数的存储不会改变缓冲区的指针和长度(它们是 8 字节的),所以这样的循环里这些读也可以外提(`store_class`、`load_blocked`);原来只有浮点存储有这条规则。

测得的时间(2 万个元素,重复 2 万遍,`a[i] = a[i] * 0.5 + b[i] + 1.0` 之类):`f32` 0.16 秒到 0.03 秒(gcc 向量化 0.02,标量 0.09);`u8` 的加法 0.29 秒到 0.008 秒(gcc 0.04);`f64` 0.15 秒到 0.07 秒(gcc 0.04)。其余基准的指令数不变。测试 `test_vector.cf`;另外用 300 个随机的逐元素循环(6 种元素类型、随机运算、不变量、长度取 0、1、15、16、17、等于长度、比长度多 1)对照旧编译器的退出码,253 个被向量化,全部相同。

没做的:一次展开多个向量;循环体里有多个存储、归约(求和)、`i` 的步长不是 1、下标不是 `i`;`f64` 的 `fdiv` 比 gcc 慢的原因还没查。
