# 寄存器感知:设计

这篇文章是下一轮后端改动的设计。第 1、2 步已经实现,其余还没有。它解释为什么要扩大可分配的寄存器、怎样不在调用点保存和恢复寄存器,以及分几步做、每步怎么验收。现状和取舍见 [机器码后端的取舍](backend-choices.md),事实和约定见 [x86-64 后端参考](../reference/x86-backend.md)。

## 现状

- 分配器(`gen.cf` 的 `alloc_regs`)是线性扫描。每个值只有一个区间,区间由各基本块的活跃信息合成。
- 可分配的只有五个被调用者保存的寄存器:`rbx`、`r12` 到 `r15`。区间放不下时,权重(循环深度的 8 次方)最低的整个留在栈帧里。
- 代码生成器自己用六个寄存器做临时:`rax`、`rcx`、`rdx`、`rsi`、`rdi`、`r11`。`r8`、`r9` 只在调用传第 5、6 个整数参数时被写,`r10` 没有任何地方使用。
- 大多数指令已经在值所在的寄存器里直接算(`src`、`home_of`),所以多一个可分配的寄存器就是少一次栈上的读写。
- 内联发生在代码生成之前(`modopt`),分配器看到的是内联之后的代码。被内联掉的调用不算调用。

剩下的浪费主要来自寄存器太少。sieve 的内层循环里,数组指针和上界每圈都从栈里读,原因就是五个寄存器被别的值占满了。

## 目标和非目标

目标:

1. 不跨调用的值可以用 `r8`、`r9`、`r10`,可分配的寄存器从五个变成八个。
2. 调用点不保存、不恢复任何寄存器。这是现有设计最大的好处,不丢掉。
3. 用每个函数"实际会写哪些调用者保存寄存器"的摘要,让更多的值可以跨调用留在这三个寄存器里。
4. 分配器尽量让结果和第一个操作数落在同一个寄存器,去掉剩下的 `mov`。

非目标:

- 区间拆分和溢出代码。一个值要么整个区间在寄存器里,要么整个在栈帧里。
- 浮点寄存器。浮点值现在经过通用寄存器和 `xmm0`、`xmm1`,这个另做。
- 提早返回路径上少保存寄存器(收缩包装)。

## 寄存器分工

| 类别 | 寄存器 | 谁用 |
|---|---|---|
| 临时 | `rax` `rcx` `rdx` `rsi` `rdi` `r11` | 只给代码生成器,不分配给值 |
| 被调用者保存的家 | `rbx` `r12` `r13` `r14` `r15` | 任何值,包括跨调用的 |
| 调用者保存的家(新) | `r10` `r8` `r9` | 不跨会写它的调用的值 |

被调用者保存的寄存器每个函数都保存、恢复(只保存自己用到的),所以任何调用都不会破坏它们。要追踪的只有调用者保存的三个。

## 什么是调用

一条指令如果会真正发出 `call`,就叫破坏点。清单是:

- `Call`、`CCall`、`CallI`,包括 `cf_syscall`(链接器供应的桩,按普通 C 调用传参)。
- `Drop`、`Clone`(调用 glue 函数)。
- `Alloc`、`Free`(调用 `malloc`、`free`)。
- `FRem`(调用 `fmod`)。

这个清单收成一个函数 `is_clobber(f, i)`,分配器和以后的自检都用它。

一个值的区间是 `[lo, hi]`。破坏点在位置 `p`,如果 `lo < p < hi`,这个值就活过了这次调用。在位置 `p` 恰好结束的值是这次调用的参数,不算活过。

## 第一档:不活过任何调用

最简单的规则:活过任何破坏点的值,只能放被调用者保存的寄存器或栈帧;不活过任何破坏点的值,可以放 `r10`、`r8`、`r9`。破坏点的位置在分配前排成有序数组,判断一个区间是否活过某个破坏点是一次二分查找。

## 第二档:函数摘要

很多调用只会写很少的寄存器。给每个函数算一个掩码,表示它和它调用的所有函数可能写哪些调用者保存的寄存器(三位:`r8`、`r9`、`r10`)。调用者的值如果活过一次调用,只要这次调用的掩码里没有它的寄存器,就可以继续放在那个寄存器里。

- 掩码是传递的:函数的掩码 = 它自己用作家的调用者保存寄存器 ∪ 它调用的所有函数的掩码。自底向上按 `call_order` 计算。
- 保守的取值:间接调用(`CallI`)、C 函数、`malloc`/`free`、`Drop`/`Clone` 的 glue、`fmod` 都取全部三位。
- **递归的函数不会因此受益。**一个函数如果在它自己的家里用了 `r8`,它递归调用自己时就会把 `r8` 写掉,所以递归调用(包括相互递归的一组)必须取保守值。`fib` 这样的递归函数跨调用的值仍然只能放被调用者保存的寄存器。
- 掩码要进接口。增量编译里,函数的掩码变了,调用它的文件要重编,和"小函数体算接口"是同一类机制。

选寄存器时用权重:对每个候选寄存器,代价 = 活过的调用点里掩码包含它的那些调用点的权重(沿用循环深度的 8 次方)之和。代价为 0 才能用;多个候选里取最先空闲的。被调用者那边,线性扫描本来就取编号最小的空闲寄存器,各函数用的寄存器会彼此重叠,掩码就小。

第二档不做调用点上的保存恢复。有一档更激进的,允许代价大于 0,在那几个调用点前后保存、恢复这个寄存器。它需要在调用点生成存取代码,复杂度和风险都高得多,等第二档的数据出来再看值不值得。

第二档的收益有上限:池里只有三个寄存器。如果数据显示它们不够,再考虑把 `rsi`、`rdi`、`r11` 也放进池(要先改 `Load`、`Store`、`Alloc` 的聚合路径和调用序列对它们的占用)。

## 调用序列不需要并行搬移

调用时参数从各自的家装进 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`。如果某个参数的家恰好是 `r8` 或 `r9`,前面的装入可能把它覆盖。这里不引入通用的并行搬移,而是用两条分配规则让它不会发生:

1. 一个区间如果在某个破坏点恰好结束(它是那次调用的参数之一),不能放 `r8`、`r9`。可以放 `r10`,它不是参数寄存器。
2. 函数入口块的参数不能放 `r8`、`r9`。序言按顺序把 `rdi`、`rsi`、...、`r8`、`r9` 存进各自的家,前一个参数的家如果是 `r8`,会覆盖后一个参数还没读走的 `r8`。

块之间的边上传参已有冲突检测(`edge_copy` 的 `hazard`,按家的编号比较),对任何寄存器都有效。

## 分配器怎么改

线性扫描的循环不变,变的是选寄存器那一步:

1. 对每个待分配的区间 `d`,得到允许使用的寄存器集合。
2. 不活过调用的先试调用者保存的寄存器(省掉序言保存和收尾恢复),再试被调用者保存的。
3. 提示:如果 `d` 由第一个操作数 `a` 算出,并且 `a` 的区间正好在 `d` 的定义处结束,先试 `a` 的寄存器。块参数先试它的第一条入边上传入值的寄存器。
4. 没有空闲寄存器时,仍然是比较权重,但只在允许集合里挑被挤掉的那个。

序言保存的集合还是"用到的被调用者保存寄存器",调用者保存的不进这个集合。

## 怎么证明没有写错

典型错误是某个值在调用后被破坏,症状是偶发崩溃或结果错,所以不能只靠测试碰运气:

- 分配完之后逐个检查:放在调用者保存寄存器里的值,是否活过会写它的破坏点。违反时置 `err`,和其他生成错误一样让编译失败。
- 加一个测试,同时让十几个值活着,中间夹着调用,和不夹调用两种情况,各取值求和。
- 编译器自己编译自己,再编译一次,产物一致(已有的不动点检查)。
- `compat` 的 1023 个用例和各阶段测试全部通过。

## 分步实施

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 收出 `is_clobber`,建立破坏点表,加上自检 | 行为不变,自检不触发 |
| 2 | 加 `r10`,第一档规则生效 | 全部测试通过;记录 sieve、编译器体积、编译耗时 |
| 3 | 加 `r8`、`r9`,加上两条参数规则 | 同上 |
| 4 | 提示:第一操作数、块参数 | `mov` 数量下降,用 `objdump` 统计 |
| 5 | 函数摘要,第二档规则 | 活过调用而被迫放栈的值变少 |
| 6 | 权重调整 | 只有数据支持才保留 |

每一步单独提交,出问题可以只回退一步。

## 预期和风险

- sieve 这类带不变量的循环会明显受益,因为内层循环不再读栈。`fib` 这样的递归函数基本不受益,它的值都活过自己的递归调用。
- 第二档能救回来的是"活过一次调用,而被调用函数很小又不递归"的值。有多少要靠测量,我现在不敢保证。
- 破坏点清单漏项。对策是只有一个 `is_clobber`,并且自检会抓到。
- 以后有人在代码生成器里新增临时寄存器用法,占用了 `r8`、`r9`、`r10`。对策是在 `Gen` 的开头写明寄存器分工。
- 单区间的限制让收益有上限:真要突破就得做区间拆分,那是另一个设计。
