# 寄存器感知:设计

这篇文章是下一轮后端改动的设计,还没有实现。它解释为什么要扩大可分配的寄存器、怎样不引入调用点上的保存恢复,以及分几步做、每步怎么验收。现状和取舍见 [机器码后端的取舍](backend-choices.md),事实和约定见 [x86-64 后端参考](../reference/x86-backend.md)。

## 现状

- 分配器(`gen.cf` 的 `alloc_regs`)是线性扫描。每个值只有一个区间,区间由各基本块的活跃信息合成。
- 可分配的只有五个被调用者保存的寄存器:`rbx`、`r12` 到 `r15`。区间放不下时,权重(循环深度的 8 次方)最低的整个留在栈帧里。
- 代码生成器自己用六个寄存器做临时:`rax`、`rcx`、`rdx`、`rsi`、`rdi`、`r11`。`r8`、`r9`、`r10` 没有任何地方使用,除了调用传第 5、6 个整数参数时写 `r8`、`r9`。
- 上一轮改完之后,大多数指令已经在值所在的寄存器里直接算(`src`、`home_of`)。所以现在多一个可分配的寄存器,就是少一次栈上的读写。

剩下的浪费主要来自寄存器太少。sieve 的内层循环里,数组指针和上界每圈都从栈里读,原因就是五个寄存器被别的值占满了。

## 目标和非目标

目标:

1. 不跨调用的值可以用 `r8`、`r9`、`r10`,可分配的寄存器从五个变成八个。
2. 调用点仍然不保存、不恢复任何寄存器。这是现有设计最大的好处,不丢掉。
3. 分配器尽量让结果和第一个操作数落在同一个寄存器,让块参数落在传入值的寄存器,去掉剩下的 `mov`。

非目标:

- 区间拆分和溢出代码。一个值要么整个区间在寄存器里,要么整个在栈帧里。
- 浮点寄存器。浮点值现在经过通用寄存器和 `xmm0`、`xmm1`,这个另做。
- 提早返回路径上少保存寄存器(收缩包装)。只有当更多值落在调用者保存的寄存器里,序言里要保存的才会变少,这是顺带的效果。

## 寄存器分工

| 类别 | 寄存器 | 谁用 |
|---|---|---|
| 临时 | `rax` `rcx` `rdx` `rsi` `rdi` `r11` | 只给代码生成器,不分配给值 |
| 被调用者保存的家 | `rbx` `r12` `r13` `r14` `r15` | 任何值,包括跨调用的 |
| 调用者保存的家(新) | `r10` `r8` `r9` | 只给不跨调用的值 |

## 什么是"跨调用"

一条指令如果会让调用者保存的寄存器失效,就叫破坏点。破坏点只有这些,而且都是真正发出 `call` 的指令:

- `Call`、`CCall`、`CallI`,包括 `cf_syscall`(它是链接器供应的桩,按普通 C 调用传参)。
- `Drop`、`Clone`(调用 glue 函数)。
- `Alloc`、`Free`(调用 `malloc`、`free`)。
- `FRem`(调用 `fmod`)。

这个清单现在散在 `gen_inst` 里。设计要求把它收成一个函数 `is_clobber(f, i)`,分配器和代码生成器都用它,避免两边不一致。

一个值的区间是 `[lo, hi]`,定义在 `lo`,最后一次使用在 `hi`。如果存在破坏点 `p`,使得 `lo < p < hi`,这个值就跨调用,只能放被调用者保存的寄存器或栈帧。其余的值可以放调用者保存的寄存器。

破坏点的位置在分配前排成有序数组,判断一个区间是否包含破坏点是一次二分查找。

## 调用序列不需要并行搬移

调用时参数从各自的家装进 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`。如果某个参数的家恰好是 `r8` 或 `r9`,前面的装入可能把它覆盖,这就是并行搬移问题。

这里不引入通用的并行搬移,而是用两条分配规则让它不会发生:

1. 一个区间如果在某个破坏点 `p` 恰好结束(`hi == p`,也就是它是那次调用的参数之一),不能放 `r8`、`r9`。可以放 `r10`,因为它不是参数寄存器。
2. 函数入口块的参数不能放 `r8`、`r9`。序言按顺序把 `rdi`、`rsi`、...、`r8`、`r9` 存进各自的家,如果前一个参数的家是 `r8`,会覆盖后一个参数还没读走的 `r8`。

块之间的边上传参已有冲突检测(`edge_copy` 的 `hazard`,按家的编号比较),对任何寄存器都有效,不用改。

## 分配器怎么改

线性扫描的循环不变,变的是选寄存器那一步:

1. 对每个待分配的区间 `d`,判断它跨不跨调用,得到允许使用的寄存器集合。
2. 不跨调用的先试调用者保存的寄存器(省掉序言保存和收尾恢复),再试被调用者保存的。跨调用的只试被调用者保存的。
3. 提示:如果 `d` 由第一个操作数 `a` 算出,并且 `a` 的区间正好在 `d` 的定义处结束,先试 `a` 的寄存器。块参数先试它的第一条入边上传入值的寄存器。提示的寄存器不在允许集合里时忽略。
4. 没有空闲寄存器时,仍然是比较权重,但只在允许集合里挑被挤掉的那个。

序言保存的集合还是"用到的被调用者保存寄存器",调用者保存的不进这个集合。

## 怎么证明没有写错

这类改动的典型错误是某个值在调用后被破坏,症状是偶发崩溃或结果错。所以要有自检,而不是只靠测试碰运气:

- 代码生成器在每个破坏点检查:没有任何家在调用者保存寄存器里、并且还活着(`hi > p`)的值。违反时置 `err`,和其他生成错误一样让编译失败。
- 加一个测试,同时让十几个值活着,中间夹着调用,和不夹调用两种情况,各取值求和,结果与预期一致。
- 编译器自己编译自己,再编译一次,产物一致(已有的不动点检查)。
- `compat` 的 1023 个用例和各阶段测试全部通过。

## 分步实施

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 收出 `is_clobber`,建立破坏点表,加上自检。可分配寄存器不变 | 行为完全不变,自检不触发 |
| 2 | 加 `r10`,跨调用规则生效 | 全部测试通过;记录 sieve、编译器体积、编译耗时 |
| 3 | 加 `r8`、`r9`,加上两条参数规则 | 同上 |
| 4 | 提示:第一操作数、块参数 | `mov` 数量下降,用 `objdump` 统计 |
| 5 | 权重调整:按区间长度归一化再比较 | 只有数据支持才保留 |

每一步单独提交,出问题可以只回退一步。

## 预期和风险

预期收益:sieve 这类带不变量的循环会明显受益,因为内层循环不再读栈。fib 这样的递归函数基本不受益,它的值都跨调用。编译器自己的编译速度可能有几个百分点的变化,方向要靠测量,我现在不敢保证。

风险:

- 破坏点清单漏项。对策是只有一个 `is_clobber`,并且自检会抓到。
- 以后有人在代码生成器里新增临时寄存器用法,占用了 `r8`、`r9`、`r10`。对策是在 `Gen` 的开头写明寄存器分工,并让自检覆盖这三个寄存器。
- 单区间的限制让收益有上限:一个值只要在循环里被一次调用跨过,整个区间都必须在被调用者保存的寄存器或栈里。真要突破这个上限就得做区间拆分,那是另一个设计。

## 不做的备选

- **全部寄存器都保存在调用点两侧**:调用点要为每个活着的值生成保存和恢复,代码变大,而且要逐个决定哪些值活着。现有设计省掉了这个。
- **把 `rsi`、`rdi`、`r11` 也放进池**:它们被 `Load`、`Store`、`Alloc` 的聚合路径和调用序列占用,要先改这些路径,收益只是再多三个寄存器。可以放在这一轮之后。
