# JIT 的分层、热替换和预处理

状态:设计稿;其中的 `image()`(阶段 2)、映像缓存已实现,分层和 OSR 没有。上下文见 [JIT 后端的设计](jit-design.md) 和 [沙盒的设计](sandbox-design.md)。

## 为什么我们的 JIT 简单

- **静态类型**:没有投机优化,不需要类型守卫、内联缓存和去优化。低阶代码和高阶代码语义完全相同,只是快慢不同。
- **所有权,没有 GC**:没有安全点、栈图、写屏障,任何指令边界都能换代码。
- **自己的后端和链接**:调用约定、寄存器破坏集、重定位、代码布局全由我们定,没有 ABI 和 PLT/GOT 的岔路。
- **`.cir` 已含整模块信息**:调用图、效应摘要、循环信息都能在产出时算好。

## 分层

- 一阶(tier 0):`.cir` 的未优化形式(`opt 0`),生成快,代码慢。往返测试已覆盖 `opt 0` 和 `opt 1` 两种。
- 二阶(tier 1):`module_opt` 之后的形式,即现在的生成路径。
- 起步看静态热度:循环里的函数、`in_loop` 内联目标直接编到二阶,省掉一阶那一遍。
- 运行时热度用采样:`SIGPROF` 采样 RIP,映射到函数,超过阈值就提升。生成的代码里没有计数器。沙盒本来就要装信号处理器,基础设施共用。

## OSR:旧帧调新代码

不换栈帧。对循环头 `H`:

1. 一个 IR 变换 `make_osr(f, H)` 生成 `f$osr`:新入口块接收一个状态缓冲区,把 `H` 处活着的值读出来,再 `Br H`;然后走正常的优化和生成。
2. 一阶代码里,循环回边处放一个热度检查,命中就 `r = call f$osr(状态)`,接着直接 `Ret r`,不执行作用域末尾的 drop,因为新代码已经接管了所有权。
3. 每次调用只触发一次,栈只多一层。

状态要的是 `H` 处的**活跃集**:块参数,加上在循环外定义、循环内使用的值(它们不经过块参数)。需要算一次活跃性,`gen` 里的区间数据是现成的。

取过地址的局部变量(`Slot`)不搬:旧帧还活着,新代码把它们的地址当参数收下。

不需要去优化,也不需要反向 OSR。

## 热替换

- 函数头 8 字节对齐,头部留一个 5 字节的 `jmp rel32` 位置。换版本是一次原子写。
- 调用点的 `rel32` 保持指向函数头。以后可以直接改调用点,要求调用点对齐到 4 字节,避免跨 cache line。
- 旧代码留到没有活跃帧使用它(用代数计数,或者一直留着,代码区够小)。

## 预处理:能提前做的不放到运行时

按时刻分:

**产出 `.cir` 之前**

- 预执行纯函数:对常量输入的纯函数(效应摘要 `f_fx` 判定),在沙盒里带燃料上限跑,把结果折成常量。不确定就放弃。
- 整模块优化好再存,`.cir` 头标志已优化。
- 静态热度写进 `.cir`:每个块的循环深度。
- 验证结果按内容哈希缓存。
- 可选的剖析节:上次运行的采样结果,下次用来排布和预编译。

**加载时**

- 一遍扫完函数表,算出调用图和用到的导入,能在生成前拒绝。
- 按 `call_order` 的层并行生成,入口函数先好先跑。
- 重定位在布局确定后一次补完。
- 预生成的镜像存成文件,按 CPU 特性分版本,启动是 `mmap`。

**运行时(后台)**

- 初始化快照:跑到第一次等待输入,存线性内存。
- 预测式提升:热函数连同它常调用的子函数一起提。

所有缓存的键都含 `.cir` 内容哈希、编译器版本、CPU 特性。

## 数据:分层值不值得做(2026-11-06)

方法:`coffee2 -O0 --emit-cir` 现在产出第一阶的模块(未优化的 IR),`-O1` 产出第二阶的;`cfjit --time` 打印启动各段的毫秒数。基准是 `ir/bench` 的 11 个程序(每个取三次用户时间的最小值),另加把编译器自己(5.8 MB 的 `.cir`)当作最大的模块。

**运行速度,一阶对二阶**(`cfjit` 与原生构建同一份机器码,两者的差别在 5% 之内):

| 程序 | 一阶/二阶用时之比 |
|---|---|
| `acc`(小函数内联,常数取余) | 2.4 到 2.6 |
| `objects` | 1.36 |
| `matmul` | 1.3 到 1.4 |
| `collatz`、`sort`、`strings` | 1.05 到 1.2 |
| `fib`、`mandel`、`bits`、`sieve` | 1.0 到 1.04 |
| `hash` | 0.88(一阶更快,噪声以上) |

**启动用时**(最大的模块,5.8 MB,`cfjit --time`):读文件 5 ms,`read_cir` 到 57 ms,剪枝到 69 ms,**生成到 217 ms**,映像到 222 ms。同一个模块的一阶版本(5.1 MB)生成到 276 ms,**比二阶慢**,因为指令更多。用映像缓存时整个启动是 18 ms。沙盒模式的各段与此相同。

**优化本身的代价**在前端:编译器的 `--emit-cir` 是 0.53 s(`-O0`)对 0.71 s(`-O1`)。它发生在做 `.cir` 的时候,不在 `cfjit` 里,而 `tea jit` 缓存 `.cir`。

结论:

1. 一阶代码不比二阶生成得快(`Gen` 的用时随指令数走,而一阶的指令更多),所以"先用一阶启动、热了再换"在启动上一毫秒也省不了。分层能省的只有优化器那 0.17 s,它不在 `cfjit` 里。
2. 二阶比一阶快的幅度,多数程序在 1.0 到 1.4 倍,只有小函数密集的程序到 2.5 倍。这是 OSR 能追回的上限,而且只在程序已经在一阶里跑了很久之后才有用。
3. 最大的模块 220 ms 就能全部生成,用缓存是 18 ms。所以一直用二阶并缓存映像,比分层简单也比分层快。
4. 没有这个数据支持的东西不做:一阶生成路径、采样、`make_osr`、热替换。如果以后出现"模块大到生成要几秒"或者"同一个模块在多个未缓存的进程里启动"的场景,再回来看这一节。

## 生成速度:热点和改动(2026-11-06)

用 `valgrind --tool=callgrind` 跑 `cfjit prog.cir --no-run`(`--no-run` 生成完就退出,不运行程序;这台机器上 `perf` 没有权限)。被测的是编译器的 5.8 MB 模块,带符号构建(`-g --static`)。总指令数 44 亿,用时 222 ms。

| 热点 | 占比 | 原因 | 处理 |
|---|---|---|---|
| `verify`(IR 检查器)及其被调用者 | 约 35% | `Lower.put_fun` 对每个函数都跑;支配树的计算对每个块扫描所有块找前驱,平方级 | 先建前驱表(CSR),检查器从约 70 ms 降到 7 ms,所以**默认保持开启**(`--no-verify` 可关) |
| `Lib.find` | 11% | `reach_from` 对每个调用做线性查找 | 先建名字号到函数的索引 |
| `read_file` 逐字节 `put_byte` | 14% | 每个字节一次追加和扩容检查 | 一次扩容,直接写 |
| `Obj.sym` | 6% | 符号表线性比较 | 开放寻址的哈希索引(编译器也受益) |
| `fnv64` | 2.5% | 没用缓存也算键 | 只在 `--cache` 时算 |
| `Gen.alloc_regs` | 14.6%(改后 20%) | 位集活跃分析:块数乘值数/32 个字,迭代到不动点 | 换成 SSA 路径探索:从每个"块内先使用"的值往前驱走到定义块,指令数 4.1 亿降到 1.5 亿;生成的代码与旧算法**逐字节相同**(编译器自己的构建、三个基准的目标文件都比过) |
| `Rd.var`、`Rd.byte`、`get_col` | 约 19% | 每个值一次调用 | `var` 加单字节快路径(效果在噪声里) |

结果:启动从 222 ms 降到 109 ms(读 `.cir` 43 ms,生成 60 ms,映像 4 ms),其中 IR 检查器开着,占 7 ms。编译器自己的编译(`--static` 构建)从约 0.71 s 到 0.66 s,因为 `Obj.sym` 和 `Txt.put_all` 的改动是共用的。读 `.cir` 现在是每个值一次变长整数解码,约 430 万个值,是剩下最大的一块。

## IR 检查器要不要开,会不会影响安全

- **沙盒的隔离**不依赖它:隔离靠的是机器码验证器(`sbxcheck.cf`),不管 IR 对不对,生成的字节过不了验证器就不运行。
- **宿主进程的健壮性**依赖它:不可信的 `.cir` 经过 `read_cir` 的结构检查后,仍可能是类型不对的 IR,而 `Gen` 对这样的 IR 没有承诺(最坏是 `Gen` 自己索引越界而陷阱,Coffee 的数组访问会检查下标,所以是崩溃,不是内存破坏;但 `peek`/`poke` 这类低层操作在编译器里有)。所以对不可信输入,检查器是第二道防线,不该关。
- 因此现在默认开,并且在失败时拒绝运行(退出码 2)。让它开着的代价是 7 ms,是靠把平方级的支配树计算改成线性才换来的。
- 这次开启时发现了一个检查器的误报:`peek8(16)` 之类的运行时访存在 IR 里是 `load i8 <i64>`(地址是整数),检查器原来只认指针。已改成两者都认。编译器自己的流程一直忽略检查结果,所以这类误报没人看见。

关于"流式处理会不会比关闭好":检查器的代价是它自己的计算量,把读、检查、生成串成流水线不会减少这些计算,只会减少内存(不用整个模块同时在内存里)。能减少用时的是并行(不同函数同时检查和生成),那是另一回事,见上面的"按 `call_order` 的层并行生成"。先把检查器本身变便宜,比关掉或者流式处理都更好,这也是这次做的。

## 第三阶:先看缺口在哪里

方法:把六个基准手工改写成 C,用 `gcc -O2` 和 `clang -O2` 跑,与我们的 `-O1`(最高档)比用户时间。

| 程序 | 我们 | gcc -O2 | clang -O2 | 我们/gcc |
|---|---|---|---|---|
| `fib` | 0.13 | 0.03 | 0.06 | 4.2 |
| `mandel` | 0.19 | 0.10 | 0.10 | 1.9 |
| `matmul` | 0.19 | 0.13 | 0.13 | 1.45 |
| `collatz` | 0.15 | 0.09 | 0.08 | 1.6 |
| `sort` | 0.38 | 0.29 | 0.29 | 1.3 |
| `bits` | 0.39 | 0.40 | 0.38 | 1.0 |

差距在 1.3 到 2 倍(`fib` 例外,gcc 把一个递归调用变成循环)。看 `mandel` 的内循环反汇编,缺口不是需要剖析数据才能补的东西,而是普通的代码生成缺陷,对所有阶都有用:

1. **循环携带的值经过内存。**块参数的拷贝在"某个实参正是已写入的形参所在的寄存器"时走栈上的暂存区:每圈 3 次存加 3 次取。已改成寄存器间的并行移动(没有被后面的移动读取的寄存器先写,环用 rcx 或 xmm0 断开),`mandel` 从 0.19 降到 0.11,与 gcc 的 0.10 相当。
2. 常量(`2.0`、`4.0`)每圈重新用 `movabs` 加 `movq` 生成。没改。
3. 浮点比较后接分支生成的是 `ucomisd; seta; movzbl; ...; test; je`,不是 `ucomisd; jbe`。没改。

所以"第三阶"当前的答案是:缺的是基本的优化和代码生成,不是运行时重编译;这些一旦做了,所有代码都受益,也不用换代码的机制。要剖析驱动的东西(热块排布、热点内联)是之后的事,它们的收益要在这些缺陷修完之后再量。

## 长运行优化的机制

问:既然多数程序一阶二阶差距不大,能不能做"长时间运行后再优化"的机制?

可以做,架构也允许:静态类型没有去优化,没有 GC 所以任何指令边界都能换代码,`make_osr` 和热替换的做法在上面已经设计好了。缺的不是机制,而是**换过去的东西**:`-O2`、`-O3` 现在和 `-O1` 是同一档,二阶就是我们能做的最好的代码,而它在启动时 77 ms 就能全部生成。机制要有意义,得先有一个比二阶更贵、更好的第三阶,例如:

- 按运行时采样排布代码、决定内联(依赖剖析的优化,启动时没有数据,只能运行后做);
- 更好的寄存器分配或循环优化,贵到不适合每个函数都做;
- 针对运行时才知道的值(循环次数、常量参数)特化,但静态类型的程序里这类机会少。

所以顺序应该是:先有第三阶的优化,量出它对热点的收益,再做换代码的机制。反过来先做机制,换过去的还是一样的代码。

## Float compare and branch

A float `<`, `<=`, `>`, `>=` whose only use is the branch right after it now sets the flags once
(`ucomisd`) and jumps on `ja`/`jbe`-style conditions; the `setcc`/`movzx`/`test` sequence is gone.
An unordered operand sets CF, so `a` and `ae` are false for NaN, as the compare requires. `==` and
`!=` still go through `setcc` pairs (they need the parity flag too). Constants such as `2.0` are still
loaded with `movabs`+`movq` at each use; hoisting them out of loops is not done yet.
