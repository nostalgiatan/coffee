# 跨平台框架:分层、接口和实施顺序

> 总体架构和路线以 `architecture.md` 为准;这份文档保留目标表字段和各系统要点的细节。


这份文档把已经做的(`ir-lowering-design.md`、`target-runtime.md`、`backend-sharing.md`、`sandbox-design.md`、`sandbox-pointers.md`)收成一个框架,并定出剩下的步骤。原则只有一条:**一个目标 = 一份数据 + 一小组函数;其余代码不知道目标是谁。**

## 1. 范围

要支持的目标(按"系统 × 架构"):

| | x86-64 | aarch64 | riscv64 |
|---|---|---|---|
| Linux | 有 | 有(里程碑 3) | 有(编译器一侧,见 [riscv64 后端](../reference/riscv64-backend.md)) |
| Windows | 将来 | 将来 | |
| macOS | 将来(无 W^X 直通) | 将来 | |

不在范围内:iOS 的 JIT(系统不允许);32 位目标;不是 ELF/PE/Mach-O 的格式。编译器自己(`coffee2`)仍是 x86-64,但能交叉编译。

## 2. 分层和每层的契约

```
源码 → 前端 → IR(SSA) → modopt → legalize ─┬→ 后端(目标) → 目标文件 → 链接器(目标) → 可执行
                          .cir 在这里落盘  │                                      └→ JIT 映像 → 加载器(系统)
                                           └→ 沙盒验证器(目标)
```

- **IR 及之前**:与目标无关。`.cir` 是 legalize 之前的可移植对象。
- **legalize**:把目标不原生支持的操作改写成目标支持的(`Switch`、`Alloc`、常数除法等)。读 `TargetSpec` 里的"支持哪些操作"。
- **后端**:`gen_function(g, f, rs, sy)` 一个入口。它**用**共用服务(第 4 节),**提供**指令选择和编码。
- **目标文件和链接**:对象格式(ELF 现在有,PE/Mach-O 将来)和重定位种类按目标表驱动;`cfld` 和内存里的 JIT 链接器读同一张表。
- **运行时**:`rt/src/min.cf` 是所有系统共用的部分,`os_<系统>_<架构>.cf` 是系统调用或系统库的部分。
- **JIT 加载器**:按系统换内存接口(`mmap`/`mprotect`、`VirtualAlloc`/`VirtualProtect`)。

## 3. 目标的两部分

### 3.1 `TargetSpec`(数据)

每个目标一个文件(`target_x86.cf`、`target_a64.cf`,命名 `tg_`/`ta_` 前缀改为统一的 `tg_`,放进以目标命名的模块)。字段:

| 组 | 内容 |
|---|---|
| 寄存器类 | 整数池(按尝试顺序)、浮点池、每个寄存器是调用者保存还是被调用者保存、保留的暂存寄存器、帧指针、返回地址 |
| 调用约定 | 整数/浮点参数寄存器序列、返回寄存器、聚合返回地址寄存器、栈参数槽大小、栈对齐、影子空间(Win64 的 32 字节) |
| 帧 | 帧头大小、最大帧、最大立即数偏移、聚合拷贝的字长 |
| 操作支持 | 原生支持的 IR 操作集(legalize 读它)、常数除法是否用 `SMulHi`、能否 `cmov` |
| 立即数 | 算术立即数的范围、能否表示某个常数(`aarch64` 的逻辑立即数规则)、地址偏移范围 |
| 沙盒 | 区域起点寄存器、地址暂存寄存器(如需要)、影子帧寄存器、受保护寄存器、访存形式、位移范围 |
| 对象/链接 | 重定位种类表、对象格式、入口约定、函数对齐 |
| 系统 | `cf_syscall` 的桩字节(已在 `ld/src/stub.cf`)、运行时的哪个 `os_*.cf` |

规则:**后端代码里出现的目标常数,必须来自这张表。** 现在 `target_x86.cf` 已经按这个做了一部分(池、保留寄存器、沙盒寄存器角色),`target_a64.cf` 是另一种风格(函数名 `ta_*`)。第一步是让两边的**字段名一致**,共用代码才能读它们。

### 3.2 后端函数(代码)

每个目标必须提供的函数,签名固定:

| 函数 | 作用 |
|---|---|
| `gen_function` | 生成一个函数的机器码 |
| `emit_access(acc)` | 发出一次访存(见 5.1) |
| `emit_move`、`emit_load_imm` | 寄存器间移动、常数物化 |
| `emit_call(call)` | 调用序列(参数放置、返回值取回) |
| `emit_prologue/epilogue` | 帧的建立和拆除 |
| `encode_*` | 汇编器 |
| `verify_sandbox` | 沙盒验证器的解码 |

只有这些是 ISA 专有的。

## 4. 共用服务(`regalloc.cf`、`frame.cf`、`edges.cf`)

按 `backend-sharing.md` 的分类抽取。接口:

```
LiveRanges   = live_ranges(g, f, rs, spec)          # 已共用,改名
Allocation   = linear_scan(g, f, spec.classes)      # 骨架共用,寄存器类由 spec 给
FrameLayout  = layout(g, f, rs, spec.frame)         # 栈帧和影子帧
EdgeCopies   = edge_copies(g, f, rs, e, mover)      # 冲突判断共用,"怎么挪"由目标给
```

线性扫描的差别(x86 的调用者保存池与 a64 的全部被调用者保存)用**寄存器类**表示:每个类有池、`caller_saved` 位掩码、是否可以跨调用持有。x86 的 `cm`/`restr` 约束写成"值在调用之间存活时,只能用被调用者保存的寄存器"这一条规则,a64 的池全是被调用者保存,约束自然为空。

## 5. 沙盒

沙盒的合同在所有目标上相同:**不可信的 `.cir` 不能让代码读写线性内存之外的东西,不能执行线性内存之外的代码,也不能做清单之外的系统调用。** 实现分三层。

### 5.1 访存口

`Asm.mem` 是 x86 的唯一访存口(已做)。接口提升为 `Access`(第二个目标需要时才引入;aarch64 已经有了,所以现在可以引):

```
class Access: kind, width, base, index, scale, disp, pfx
```

目标提供 `emit_access`,按 `spec.sandbox.mode` 选择发出方式:

| 模式 | x86-64 | aarch64 |
|---|---|---|
| 无沙盒 | 原样 | 原样 |
| 段(`gs`) | `67 65` 前缀 | 不适用 |
| 基址 | 先算 32 位地址再 `[r15 + r13]`,或(偏移式指针)`[r15 + r + disp]` | `[x28, wN, uxtw]` |

### 5.2 指针模型

采用偏移式指针(8 字节存储,值是区域内偏移),不变量"高 32 位为零"由生成方式保证,由验证器的数据流证明(`sandbox-pointers.md`)。`gs` 保留到基址模式的开销降到可接受(不高于 `gs` 的两倍)再删除。pkeys 是可选加速,不在基础框架里。

### 5.3 验证器的规则成数据

各目标的解码不同,但规则相同:

- 允许的内存操作数形式,位移范围;
- 受保护寄存器的写入规则(区域起点不许写,地址暂存只许一条指令写,影子帧基址不许写);
- 禁止的指令类(系统调用、陷入、间接转移、改段基址、写栈指针除帧操作);
- 终止和目标:最后一条不落入后面的代码,直接转移落在指令边界。

规则表由 `TargetSpec.sandbox` 给出;共用的反例集(每个目标一份字节序列)保证新目标不漏项。

### 5.4 宿主调用

按 `jit-design.md` 的跳板设计:每个登记的宿主函数带签名,跳板检查指针参数和长度并加基址,返回指针时减基址。沙盒的指针模型决定跳板怎么做(偏移式指针:检查 `p + len` 不越界、加基址),所以这一步放在指针模型之后。

## 6. 对象和链接

- **重定位**:种类表按目标(`x86_64`:`PC32`、`PLT32`、`64`;`aarch64`:`CALL26`、`ADR_PREL_PG_HI21`、`ADD_ABS_LO12_NC`、`LDST*_LO12` 等),`cfld` 和内存链接器读同一张表。
- **格式**:`ObjectFormat` 提供节、符号、重定位的写出;ELF 现在有,PE(COFF)是下一个。每个格式一份写入器,同一份 `Obj` 内存表示。
- **库**:`--pic` 的隐藏可见性规则对 ELF 是 `st_other`,对 PE 是不导出;`cf_syscall` 之类的桩由 `TargetSpec` 的系统字段给出(已做)。

## 7. 系统层

- **运行时**:Linux 用系统调用号(已拆),Windows 用 `kernel32`/`ntdll` 导入(没有稳定的系统调用号),macOS 同样走库;所以 `os_windows_*.cf` 不是"换号码",而是"换成对导入函数的调用",这要求运行时能声明和调用导入——`.cfc` 的 `c fn` 已经可以。
- **JIT 加载器**:`mmap`/`mprotect` 换成 `VirtualAlloc`/`VirtualProtect`;aarch64 要在写入代码后做指令缓存同步(`dc cvau`、`ic ivau`、`dsb`、`isb`,或 `__clear_cache`),x86 不需要;macOS 的 `MAP_JIT` 和写保护切换。
- **陷阱**:Linux 用信号;Windows 用结构化异常处理(SEH/向量异常处理);沙盒的陷阱出口在各系统各一份。

## 8. 测试矩阵和门槛

每个步骤都要满足:

1. **x86-64 输出逐字节不变**:语料(`/tmp/corp/run.sh` 的做法,把它收进 `tools/` 并入库)新旧编译器对比。
2. **aarch64 输出逐字节不变**:`ir/tools/a64diff.py`、`a64cases.py` 加一个 sha 清单。
3. 每个阶段的 `tea test`,`compat` 全过;
4. 沙盒:`test_sandbox*.cf`、`compare.sh`(`SANDBOX=1`、`SANDBOX=base`)、两套验证器的反例集;
5. 自举不动点:种子刷新,再构建一次逐字节相同。
